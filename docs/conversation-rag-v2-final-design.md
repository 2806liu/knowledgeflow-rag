# 项目 A：会话式文档问答最终架构设计 v2

日期：2026-10-15
状态：架构与验收设计定稿；两项产品取舍已获用户确认。六模块已实现并接入；自动、真实模型、助手初审和浏览器验收以evaluation/results/conversation-v2中的实际报告为准。
范围：仅项目 A（RAG项目）。不导入、读取、调用或启动项目 B。
验收计划：evaluation/conversation-v2/acceptance-plan.json。


## 已确认的范围与决策

- 本轮四项业务能力：文档概述、连续附件、上传恢复、多轮理解；增加记忆管理与上下文预算两个共享模块，共六个职责模块。
- 用户确认：单独追加 B 成功后“这篇”默认指向 B，A 保留在当前会话；同批添加多份文件时先澄清对象。
- 用户确认：本轮实现近期完整轮次、滚动摘要、结构化状态；语义相似度与时间衰减评分留到后续对照实验。
- 保持项目 A 独立运行，复用自己的 SQLite、解析/OCR、检索、重排、LLMClient 和评测工具。
- 原文档事实由原文证据支持；历史、摘要、查询改写用于理解问题，不单独充当原文依据。
- “设计定稿”不等于代码已实现或指标已达标；新增场景自动结果与语义/浏览器验收分别保存，不能仅凭自动通过宣称全部验收。

### 六个模块及唯一职责

| 模块 | 负责 | 不承担的相邻职责 |
|---|---|---|
| ConversationService | 会话、附件关联、焦点、范围版本和每轮快照 | 不执行OCR或LLM摘要 |
| IngestionService / UploadManager | 文件任务、期限、重试、协作取消、发布和UI恢复 | 不决定问题意图和文档事实 |
| QueryResolver | 意图、指代、条目定位、检索问题改写与澄清 | 不将历史回答当文档证据 |
| OverviewService | 指定文档全篇取证、分层概述和原始来源映射 | 不替代一般知识检索与索引 |
| MemoryManager | 完整轮次选择、滚动摘要、主题及历史条目定位 | 不拥有文档范围的权威状态 |
| ContextBuilder | 所有LLM阶段的输入预算和上下文组装 | 不读库、不调用LLM、不自行生成摘要 |

共用LLMClient承担调用、期限、有限重试、token/耗时、错误分类；Store承担存储；主流程只编排。

## 1. 目标与现有差距

本轮明确交付四项能力：
1. 选中文档后可以请求文档概述，真实调用 LLM，并回溯到原始 chunk。
2. 同一会话多次上传，保留已有资料，展示每个附件状态和实际问答范围。
3. 上传有超时、重试、取消与状态恢复；故障不会永久禁用全部入口。
4. 检索前理解“这篇”“刚才第二点”“再详细一点”，保持原问题可审计。

复用：解析/OCR、清洗切块、SQLite、BM25/Dense/Hybrid、重排、相邻证据、LLMClient、引用校验、逐句复核。
当前问题：原问题直接 Top-4；概述零命中后跳过 LLM；连续上传替换选择；前端 fetch 无主动期限；历史只用于生成而未参与检索解析。
保持：普通知识问题依旧进入既有检索链路；真实模型失败与无证据拒答分别记录。

## 2. 数据流与模块边界

上传路径：
文件选择/拖放 → 上传任务 → 原文件暂存 → 解析/OCR → 切块/索引 → 发布就绪文档 → 追加会话关联。
前端同时展示传输状态和后台处理状态；传输完成不等于可检索。

问答路径：
原始问题 + 会话资料范围快照
→ MemoryManager 获取最近完整轮次、历史摘要和结构化主题
→ 问题解析 QueryResolver（判断意图、主题、序号、歧义）
→ 概述意图进入 OverviewService，具体问答进入既有检索/重排/补齐
→ ContextBuilder 控制输入预算
→ LLMClient 生成
→ 校验引用与结构
→ 保存回答单元、范围快照、来源版本、运行事件
→ MemoryManager 更新主题与条目定位，达到阈值时安排滚动摘要
→ 页面展示回答、来源与缺失/歧义提示。

拟新增职责文件（均为计划路径）：
- app/conversation.py：会话、附件关联、活动文档、范围版本、每轮快照。
- app/ingestion.py：摄取任务状态机、期限、幂等、协作取消、原子发布与清理。
- app/rag/query_resolution.py：意图分类、指代/序号解析，输出独立检索问题。
- app/rag/overview.py：全篇取证、短文直读、长文分层概述、版本缓存。
- app/rag/context_builder.py：所有模型阶段共用的纯上下文预算工具。
- app/rag/memory.py：完整轮次、滚动摘要和结构化主题；与会话范围分离。
- 前端拆分为 conversation.js、attachments.js、upload_manager.js；app.js 保留页面编排。
- main.py 只做请求校验、依赖调用和状态码映射；services.py 只做问答流程编排。
- schemas.py/store.py 增加契约与持久化，不把业务流程塞入数据访问层。
- 所有新增/修改代码配中文注释和 docstring；文档不能替代代码注释。

## 3. 模块一：文档概述 OverviewService

### 输入与输出

输入：resolved intent=overview；明确的 document_ids；文档 content_revision/index_revision；摘要粒度；预算/期限。
输出：answer、answer_status、answer_units、citations、coverage、source_versions、LLM trace。
概述无需在 BM25 中命中“文章讲什么”才开始；从指定文档按结构读取内容。

### 取证与生成

- 优先从已索引的规范 chunk 按章节和位置读取，引用沿用其 ID、页码、文件名。
- 短文：所有需要覆盖的 chunk 能放入预算时，一次真实 LLM 生成主题、主要内容和结论。
- 长文：按章节/预算分批提取要点，再汇总。每条中间要点必须携带原始 chunk IDs；最终引用只指向原文，不指向不可回溯的中间摘要。
- 最终回答中的引用编号在本轮统一分配，映射到原始 chunk；不把不同页合并成虚构来源。
- 概述证据使用evidence_role=overview；未经历检索/重排的分数为null，不伪造BM25或重排分数；相应响应契约向后兼容。
- 不使用 Top-4 代替全文覆盖；记录纳入、跳过的章节/chunk 及原因。
- 缓存键包含 document_id、content_revision、index_revision、提示词版本和模型配置摘要。重解析、重建索引或删除后校验失效。
- “内容覆盖”区分原始章节被处理与摘要关键点被表达，不能用前者证明后者。
- 确认的概述请求如果只有一份就绪资料可直接确定对象；有多份且无活动文档则先澄清。
- 原文不足以概括时给出具体提示；模型超时、格式失败单独报错。部分章节失败时返回 partial_answer 并列出未覆盖部分，不能标成完整全文概述。

### 验收

- 固定概述用例的意图与文档范围正确率 100%。
- 可成功概述的样本原始章节处理覆盖率 100%；预算/失败导致不足时，100% 标记 partial_answer 和缺失范围。
- 人工标注关键点召回率：各样本 ≥80%，样本宏平均 ≥90%。
- 原子事实与实际引用原文的支持率 ≥95%；引用定位有效率 100%。
- 严重编造（数字、要求、主体、整篇结论被凭空改变）为 0。
- 成功概述中 LLM 真实调用记录覆盖率 100%；缓存命中单独标识 reused，不伪造新调用。
- 短文新鲜生成调用 1 次；长文记录每阶段调用数，受配置最大调用数和总期限约束。
- 长文尾部标注关键点必须出现在摘要要点中，避免只覆盖开头。
- 本轮必须实测用户的“这篇文章讲什么”场景，但私有真实文档报告不进入公共发布目录。

## 4. 模块二：连续附件与会话资料 ConversationService

### 持久化模型

- conversations：id、scope_mode、active_document_id、scope_revision、created_at、updated_at。
- conversation_documents：conversation_id、document_id、added_at、enabled；联合唯一。
- conversation_turns：id、conversation_id、original_question、resolved_question、intent、scope_snapshot、answer_status、answer_units、source_versions、run_id。
- 原有 messages 保持兼容；新轮次记录应引用消息 ID，避免出现两份互相矛盾的权威正文。

scope_mode：
- attached：在当前会话启用的就绪关联资料；UI 默认。
- selected：用户明确勾选的资料集合。
- all：用户明确选择全部知识库，并显示提示。
空集合不能意外退化成全库检索。

### 交互语义

- 聊天区上传成功：追加关联，已有启用文件保留。
- 重复上传相同字节：复用文档并幂等关联，不重复索引；同名不同内容作为不同文档显示。
- 单次多文件逐个显示文件名、状态、重试/取消按钮；不会因部分失败撤回其余成功文件。
- 资料就绪后才能用于取证；未就绪附件仍可见，询问其内容时提示等待。
- 上传期间允许对旧的就绪资料提问；本轮发送时冻结范围与来源版本。
- 请求发出后新附件不追加入该轮；下一轮可使用。删除/更新导致快照失效应明确重试，不偷偷换源。
- 用户确认：单独追加 B 并就绪后，关联集合追加 B，活动文档切换到 B；已有 A 保留且可显式切回。同批添加多份时活动对象需澄清，不能按最后完成的文件猜测。
- 处理完成顺序不能覆盖更新的用户操作：记录附件批次顺序和 focus_revision；旧任务晚完成时，不覆盖用户较新的手动选择或新批次焦点。
- B尚未就绪时显示处理中，不能将“这篇”静默解释为旧A；界面明确标出待处理焦点，用户可以显式选择已就绪A继续问。
- 多份资料且无明确焦点时，“这篇”先澄清；“这几篇”明确全选集合，可逐文档概述。
- 从当前会话移除只解除关联；从资料库删除为另一操作且需确认。
- 刷新恢复会话 ID、消息、资料范围和进行中任务；新会话保持隔离，可显式关联已有资料。
- 浏览器本地只保存最近会话 ID 等恢复入口；服务端持久化为权威。
- 现有本地应用尚无账户体系；会话隔离测试只证明范围行为，不宣称多用户权限安全。

### 拟新增接口

POST /conversations：新建会话。
GET /conversations/{id}：恢复状态、范围及分页消息。
POST /conversations/{id}/documents：幂等追加已有就绪文档。
PATCH /conversations/{id}/scope：调整启用集合、模式、活动文档；校验 revision 防覆盖。
DELETE /conversations/{id}/documents/{document_id}：解除关联。
POST /chat：沿用原 session_id，不再增加第二套 conversation_id；conversations.id 与 session_id 为同一标识，增加可选 scope_revision 和 request_id。
旧 session_id/document_ids 调用保留现有语义；新UI先创建/恢复conversations并默认attached模式。显式document_ids为本轮明确范围；省略时读取该会话模式和关联集合。没有新会话记录的旧客户端仍保持旧兼容语义，日志标记legacy_global。新UI空范围绝不能降级到全库。
同一session同一request_id幂等，避免重复扣费与重复消息；同会话并发生成需要顺序或明确冲突，不能同时基于互相未知的上一轮解析指代。

### 验收

连续追加已有文件保留率、实际取证范围一致率、重复关联幂等率、刷新恢复正确率均 100%。
范围外来源进入检索/概述/引用的次数为 0。
解除关联误删原文档次数为 0。
重复请求产生重复索引/重复附件条目的次数为 0。
上传与问答同时发生时，本轮快照一致率 100%。

## 5. 模块三：上传恢复 UploadManager / IngestionService

### 接口与状态

新 UI 使用：
POST /ingestions：multipart file + conversation_id + client_request_id；完整暂存并接收任务后返回 202 和 job_id。
GET /ingestions/{job_id}：阶段、计数、错误码、可否重试、关联 document_id。
GET /conversations/{id}/ingestions：恢复任务；支持按 client_request_id 查找，处理创建响应丢失。
POST /ingestions/{job_id}/cancel：服务端确认协作取消。
POST /ingestions/{job_id}/retry：新 attempt，复用 request identity，避免重复发布。
旧 /documents/upload 保持同步兼容；共用解析和发布服务，避免分叉成两套逻辑。

服务端状态：
queued → parsing → chunking → indexing → ready；
异常分支：failed、cancel_requested → cancelled、interrupted。
浏览器 transmitting 为客户端状态，不冒充服务端解析状态。

### 超时、重试、取消

- 传输使用 XMLHttpRequest 提供真实字节进度与 abort；服务端处理使用阶段与页数计数，未知进度展示进行中。
- 初始可配置值：传输总期限 120s；单次状态查询 10s；后台处理总期限 600s；测试注入更短期限。限值在能力接口和 UI 说明。
- 超时不等于任务取消：创建结果未知时按 client_request_id 恢复，先查状态再重试。
- 自动网络重试最多 2 次，有限退避；格式、大小、OCR 页数/像素超限及鉴权失败不自动重试。
- 同一文件任务状态只由该任务控制，不禁用整个会话的添加入口；默认一个处理 worker，后续文件可排队或取消。
- 单次 OCR/ONNX 调用通常不能安全强杀；取消在页/阶段检查点生效。前端先显示“正在取消”，收到服务端 cancelled 才显示已取消。
- 待索引内容先暂存，不暴露给普通检索；发布前在事务中核对取消标记与任务 attempt。
- 若 ready 发布先赢得竞争，取消返回已完成/409；不得把已完成任务伪装成已取消，更不得删除复用的旧文档。
- 若取消先被确认，禁止该 attempt 后续发布；清理其暂存和私有候选索引。
- SQLite ready 发布使用事务；Qdrant 无法与 SQLite 共事务，采用候选状态与补偿清理，查询验证文档就绪状态。当前检索策略所需索引完成后才标 ready，失败不标 ready。
- 进程重启将未完成 attempt 标 interrupted，保留可恢复记录；用户明确重试，不无限重跑。
- 队列满、磁盘不足、服务退出、页面卸载都要有可观察状态和清理策略。
- 错误码区分 UPLOAD_TOO_LARGE、UNSUPPORTED_TYPE、OCR_PAGE_LIMIT、IMAGE_PIXEL_LIMIT、OCR_UNAVAILABLE、PROCESSING_TIMEOUT、NETWORK_TIMEOUT 等；不能将所有 413 映射为文件过大。
- 所有 UI 退出路径 finally 恢复各任务按钮、重置文件输入；同一文件可重新选择。
- 传输中断尚未形成 job 时清理临时文件；重新选择文件时沿用幂等键或先恢复状态。

### 验收

故障注入后的按钮/操作入口恢复率 100%；前端确认取消或超时反馈 ≤1s（浏览器前台环境）。
客户端期限到达后的恢复 ≤配置期限+2s，服务端取消耗时单独统计，不宣称同样 ≤1s。
已确认 cancelled 的任务后续发布文档次数为 0；完成/取消竞争结果一致率 100%。
创建响应丢失、重试、重复点击产生重复发布的次数为 0。
失败、取消或重启任务被错误显示为 ready 的次数为 0。
错误分类正确率和历史文档不受影响率均 100%。
每种失败类型分别验收，不能用其他成功用例抵消永久锁按钮等缺陷。

## 6. 模块四：多轮问题解析 QueryResolver

### 契约

输入：original_question、最近完整轮次、历史 answer_units、活动文档、范围快照、版本。
输出：intent(overview/qa/clarification)、resolved_query、resolved_document_ids、
referenced_turn_id、referenced_unit_id、resolution_method、clarification_question、confidence_or_reason。
这些字段存运行记录；保存的用户正文始终为原问题，不以改写结果覆盖。

### 规则与 LLM 边界

- 第一层：处理明确选中文档、“这篇”“这几篇”、显式文档名称、明确历史编号。
- “第二点”映射到上一回答结构化 answer_units，不把引用 [2] 当第二点。
- 追问“再详细一点”引用最近可定位的实质回答主题与来源；上一轮是拒答/错误时不虚构主题。
- 第二层：规则无法确定时，可调用现有 LLMClient 输出结构化解析；校验文档 ID、历史 ID、范围，输出不得扩权。
- 多候选歧义先澄清；不能凭模型自信任选文档。
- 改写负责表达用户意图，不创造文档事实；历史回答只用于定位，不作为新答案唯一证据。
- 非概述请求用 resolved_query 进入检索，再生成带新证据的回答；无证据依旧走拒答。
- 提交后资料范围被改变时按该轮快照处理；历史引用已删除/重解析需重新取证。
- 对话理解支持本轮这四类场景，不新增通用 Multi-Agent、复杂长期记忆或联网搜索。

### 验收

20 条多轮固定序列，意图/对象/检索问题联合正确率 ≥95%（至少19/20）。
所有歧义用例澄清率 100%；跨会话串用、越出当前范围、把引用编号当条目序号次数均为 0。
可回答的追问必要证据 Recall@4 宏平均 ≥90%；逐案保存原问题与改写问题的对照。
重复相同问句的两轮可分别追溯，无覆盖或错配轮次。
原问题、改写、解析依据和来源版本运行记录覆盖率 100%。

## 7. 共用上下文与来源约束

ContextBuilder 统一预算：
系统提示 + 原问题/解析结果 + 完整历史轮次 + 本轮证据
≤ 模型窗口 − 输出预留 − 安全余量。

- 配置声明可用窗口和计数方法，未知模型使用明确标注的保守估算；不伪称精确 token。
- 历史与证据一起计费；先保留当前请求、必要证据，按完整轮次移除较早历史。
- 必要证据装不下时分阶段处理或明确 partial_answer；不能静默裁剪后声称完整。
- 概述与普通检索来源都使用原始 document_id/page/chunk_id/snippet。
- 缓存和历史来源不是永久有效；重解析/删除后检查版本。
- 对回答 answer_units 校验文本与所含引用一致；编号校验不能充当语义支持率。
- 每轮事件含 scope_snapshot、query_resolution、context_budget、overview/retrieval、llm、citation_check、workflow。
- LLM 调用、耗时、token、缓存和失败均如实记录，不暴露密钥。

## 8. 测试集与指标定义

80 个新增验收用例：概述12、连续附件12、上传恢复16、多轮理解20、记忆管理12、上下文预算8。
以下清单源于设计计划；实施结果另见2026-10-15交付报告。公开合成fixtures及80项自动测试现已生成，真实语义和浏览器门槛分别验收。
测试资料使用可公开的合成文档，含短文、长文、扫描/混排、同名异文、同字节重复文档。
每条保存 case_id、输入序列、预期范围、必要证据、失败/歧义行为、检查项。
实施时先生成 fixture、人工核对 gold，然后以 SHA256 冻结语料、用例与关键点；开发集与独立验收集分别报告，不在同一批验收题上反复调参后称独立验收。

指标：
1. 关键点召回 = 被正确表达的 gold 关键点数 / gold 关键点总数，先逐题再宏平均。
2. 章节处理覆盖 = 已成功处理的非空应覆盖章节数 / 非空应覆盖章节总数；并记录 chunk 覆盖。
3. 引用定位有效 = ID 属于本轮范围且版本一致、页码正确、snippet 来自对应原文。
4. 引用支持率 = 被实际引用原文支持的原子事实数 / 已复核原子事实数。
5. 解析联合正确率 = 意图、对象、序号/主题和改写语义全部正确的样本数 / 样本总数。
6. 范围一致率 = 实际取证文档集合符合发送时 scope_snapshot 的请求数 / 检查请求数。
7. 检索 Recall@K 沿用现有评测对必要证据的定义；概述不能套 Top-K 命中替代章节/要点覆盖。
8. 恢复率、取消后发布数、重复发布数按故障类型逐项统计；分母为 0 报 N/A。
9. p50/p95 延迟、TTFR、每轮 LLM 调用数、重试数、token 与估算成本单独报告；少于20个成功样本不宣称稳定 p95。
10. TTFR 为附件状态/任务受理首次可见时间，不伪装成答案首 token；当前不要求回答流式输出。

语义指标由助手初审+独立人工确认，LLM judge 只作辅助；引用归属、字符串包含、状态码检查不能自动证明摘要正确。
支持率 ≥95% 外还要求严重编造为 0；任何越范围来源/已确认取消后发布均为阻断项。
开发测试通过不能当成全部语义验收；待审题保持 pending，不计入已通过。

## 9. 执行层次与回归门槛

1. 模块级：注入 Fake LLM、假时钟、受控解析器；验证路由、快照、状态机、幂等、预算和失败分支。
2. API 集成：隔离 SQLite/任务目录，真实 PDF/图片编解码，覆盖生命周期与取消竞争；不得影响日常资料。
3. 真实模型：实际容器 OCR + LLM，核对概述、指代追问、引用原文，保存完整 trace。
4. 浏览器端：必须真实点击/选文件/连续上传/取消/刷新；仅接口测试不能代替界面验收。
5. 历史回归：原有103项回归全通过（实际以实施前重新枚举为准）；35题检索与40题答案集在同语料/模型配置下保存前后结果。
6. 普通知识问答的 Recall@4/MRR@4 不低于冻结基线；新长文/追问题单列，避免靠混合统计掩盖退化。
7. 原有语义复核结论绑定旧报告哈希，生成新答案必须重新复核，不能继承“人工已确认”。
8. 负向问题保留固定拒答与不编造检查；资料处理中、范围不清、上游失败分别显示，不全部称资料不足。
9. 证据不足不强行补通用知识；本轮不引入外部联网知识或图像 VLM。

性能验收：
- 指定宿主、容器、模型、文档页数、输入token、并发数、缓存状态和网络条件。
- 本地状态查询 20 次 p95 ≤1s；单次正常上传/解析无故障的受理反馈 ≤2s（文件传输完成后计）。
- 取消按钮前台反馈 ≤1s；服务器协作取消单独记录检查点延迟。
- 无新增 LLM 的普通 QA 编排开销 p95 较相同基线增加 ≤100ms；需≥20次配对样本，排除模型/网络生成时间。
- 概述/改写记录端到端与分阶段延迟，在配置期限内结束或明确超时；不同模型速度不作统一秒数承诺。
- 重试次数、队列长度、最大摘要批次/调用数、输入预算都有硬上限并注入测试。

## 11. 共享模块五：会话记忆 MemoryManager

### 状态所有权与数据

- ConversationService拥有附件关系、scope_mode、active_document_id及其revision；MemoryManager只读这一权威快照。
- MemoryManager拥有current_topic、topic_entities、last_substantive_turn_id、answer_units定位及摘要派生状态。
- 原始messages/turns保留，摘要不删除原始对话；多轮条目用turn_id/unit_id关联。
- 新表conversation_memory：session_id、summary_text、summary_revision、covered_until_turn_id、source_turn_ids、source_history_digest、topic_state、updated_at。
- 摘要记录对应历史版本、来源轮次、生成模型和提示词版本；防止重复压缩或摘要覆盖更新的对话。
- answer_units含unit_id、顺序、标题/主题、正文、cited_chunk_ids和source_versions；“第二点”按条目序号定位，不按[2]定位。
- 文档焦点由本轮快照确定；新上传B后的默认指代规则按用户已确认的策略执行。

### 记忆组织

1. 当前问题始终保留，历史不重复加入当前用户消息。
2. 优先保留最近完整问答轮次；未完成轮次和工具错误记录不伪装成已完成回答。
3. 超过历史预算时，较早轮次进入滚动摘要；明确指代的历史条目单独加载并固定保留。
4. 摘要保留讨论主题、用户要求、已讨论条目、待解决问题，以及说法来源归属；用户猜测、模型回答和文档证据不能混写成已核实事实。
5. 用户纠正优先于旧主题；保留“已被纠正”的状态，后续不重复使用被撤回的说法。
6. 摘要只概括较早区间，最近窗口不重复摘要；摘要覆盖水位单调前移。
7. 增量压缩可在答复后后台进行，前台预算始终独立生效。摘要未就绪/生成失败时使用已验证旧摘要与近期完整轮次，必要时澄清，不能阻塞整会话或捏造历史。
8. 摘要发布使用history digest与revision检查，过时生成结果不能覆盖新状态。
9. 明确引用很早的一轮时可按turn_id读取原轮次；本轮不实现所有历史的向量检索。
10. 选择摘要或原始历史只用于问题定位；最终答案重新从当前有效原文取证。

### 初始可调默认值

- 最近3个完整轮次为优先窗口；这不是硬保证全部装入模型，最终由统一预算约束。
- 历史原文与摘要合计目标上限2000计数单位，摘要目标上限600；单位与token_count_method一起记录。
- 达到阈值才摘要，避免每轮重做；每次压缩最多一次模型调用，超时失败不无限重试。
- 模型可用窗口不足时收紧历史预算；当前问题/固定提示本身超限则明确报错，不静默截断。
- 上述默认是工程起点，实施时用固定测试集校准并记录配置版本。

### 验收：12条记忆用例

- 当前问题、必要指代条目保留率100%；最近轮次按完整问答保留率100%。
- 摘要source_turn_ids、覆盖水位与原始轮次对应正确率100%。
- 摘要受人工标注的主题/约束保留率≥95%，关键用户纠正保留率100%。
- 摘要出现无来源新事实、不同会话内容、重新启用已撤回说法均为0。
- 摘要失败/并发/重启不导致消息丢失或永久阻塞；旧摘要不能覆盖较新revision。
- 自动检查检查轮次/版本/结构；语义保留与摘要漂移需人工复核。
- 无需摘要的短对话额外摘要调用为0；达到阈值才产生有记录的真实调用。

## 12. 共享模块六：ContextBuilder

### 输入与输出

输入为不可变的PromptContext：系统提示、原问题/解析信息、历史窗口与摘要、原始证据、模型能力、输出预留和安全余量。
输出为messages、kept/dropped items、token_count_method、estimated_or_exact_input、reserved_output、remaining_budget、partial_coverage。
这是纯预算与组装模块；不隐式读取其他会话，不触发模型调用。

### 预算规则

- 最终模型输入全部计费：系统提示、消息结构开销、问题、历史摘要、完整轮次、证据文本及引用封装。
- 输入预算 = 声明的模型窗口 - 输出预留 - 安全余量；输入构造完成后再次校验。
- 有准确兼容tokenizer时按其计数；未知模型采用明确标记的保守估算，并留消息开销与安全余量。估算值不宣称等于服务商usage。
- 先固定系统规则、当前问题和必要证据；明确历史指代所需条目优先。
- 可裁剪项包括较早完整轮次与冗余证据。不能保留半个问答轮次、裁掉引用来源后保留对应事实或默默截断用户问题。
- 必要证据过长时，按章节/子问题分阶段处理；仍不足时标记partial_answer或明确无法完整回答。
- 概述map/reduce、查询解析、历史摘要和最终生成分别执行同一预算检查。
- 生成后使用实际usage校准估算误差，报告配置与计数方法，不把估算token作为实测token发布。
- 上下文来源版本失效时重新取证或明确错误；不能把失效来源悄悄塞回预算。

### 验收：8条预算用例

- 按声明计数方法的输入预算合规率100%；每阶段LLM调用均有预算trace。
- 系统规则、当前问题、必要指代对象在有效请求中保留率100%。
- 轮次完整性、引用映射完整性、被裁剪对象及原因记录率100%。
- 必要内容装不下时明确分阶段/部分回答/超限，不出现“静默缺项但声称完整”。
- 对未知模型计数标记正确率100%；实际usage和估算分开存储。
- 模型窗口/输出预留非法配置应在启动或请求入口拒绝。

## 13. 受控执行与阻断验收

- 每轮限制query resolution最多1次逻辑生成；实际请求尝试次数受LLMClient有限重试和本轮总期限约束，分别记录逻辑调用和HTTP尝试。
- 概述初始最多24次实际模型请求尝试（包含重试），总流程期限240秒；同一文档版本成功结果可复用，缓存必须明确命中。
- 继承LLMClient有限重试，但总流程期限约束全部尝试及退避；到期不能继续后台无界扣费。
- 状态接口、取消、错误恢复均可无需真实模型做故障注入测试；概述正确性、多轮语义及OCR必须另行真实验证。
- 80个场景中任何阻断项失败都不能以平均分抵消：范围越界、确认取消后发布、重复发布、消息丢失、严重编造、预算静默突破。
- 语义验收的所有应审样本均须完成复核；pending不得从分母剔除后宣称整个集通过。
- 复核应保存实际模型/配置、报告SHA256、支持原文、关键点判定和复核身份。
- 模块级/集成级/真实模型/浏览器结果分别报告，Mock不能替代真实LLM，接口不能替代点击验收。

## 14. 延后事项：历史相关性与时间衰减

用户已确认本轮延后；不作为80项功能验收的上线依赖。
后续实验比较：近期窗口基线、纯语义历史检索、语义加时间衰减。
相似度需统一标度，限定同会话和有效资料范围；显式指代、当前问题和活动文档先按规则固定，不受衰减过滤。
候选公式可采用带下限衰减：
score = similarity × [lambda + (1-lambda) × exp(-delta_rounds/tau)]。
lambda/tau只在开发集选择，验收集独立冻结。评分不等于事实可信度。
比较历史定位准确率、必要历史召回、最终答案关键点/引用支持率、输入token和耗时；无收益则保留简单基线。
